# 資料整理方式

## 核心問題
你現在手上有兩個「各自殘缺」的資料來源,要整理成一份「西子灣現在能不能下水」的統一資料。整理方式分三層:

## 第一層:標準化(把兩個來源攤平成同一種格式)

不管資料從哪個測站來,先轉換成你自己 App 內部統一的格式,例如:

```json
{
  "location": "西子灣",
  "observedAt": "2026-07-15T07:00:00+08:00",
  "tide": {
    "height": 1.14,
    "level": "漲潮",
    "source": "C4P01"
  },
  "wave": {
    "height": 2.2,
    "period": 6.5,
    "direction": "SW",
    "source": "COMC08"
  },
  "wind": {
    "speed": 5.6,
    "scale": 4,
    "direction": "SSE",
    "source": "COMC08"
  },
  "seaTemperature": {
    "value": 31.0,
    "source": "C4P01"
  }
}
```

這樣一來,不管你之後資料源怎麼換(例如找到離西子灣更近的浮標),App 的其他部分都不用改,只要負責「轉換」的這一小段程式改就好。這是軟體設計常說的**關注點分離**——資料怎麼來 vs. 資料怎麼用,分開處理。

## 第二層:處理缺值(「由新到舊找第一筆有效值」)

因為兩個測站都有「最新一筆是 None」的狀況,整理邏輯要這樣寫:

```
對每個測站的 49 筆資料:
  由新到舊掃描
  找到第一筆該欄位不是 None 的資料
  記錄這筆的數值,以及它的時間戳記
```

**重要:要把「這筆資料是幾點的」也存起來**,不要只存數值。因為如果最新有效資料是 3 小時前的,你的 App 應該老實顯示「更新於 3 小時前」,而不是假裝這是即時資料——這也是對使用者的誠實揭露,避免有人以為是當下的即時狀況。

## 第三層:合併成單一地點的完整快照

把 C4P01(潮汐/海溫)和 COMC08(浪高/風速)兩份「標準化+處理過缺值」的資料,依照時間對齊,合併成上面那個統一 JSON。這一步做完,才能餵給你的紅黃綠燈判斷邏輯。

## 建議的技術架構(重要,別讓 App 直接呼叫政府 API)

不要讓手機 App 每次開啟都直接打政府的 API。原因:
1. **安全性**:你的 API 授權碼會被放在 App 裡,容易被反編譯偷走
2. **穩定性**:政府 API 偶爾會慢或斷線(前面你也遇過查全臺資料跑很久的狀況),直接影響使用者體驗
3. **效率**:兩個資料源要合併運算,這種邏輯適合放在後端,不是手機上

**建議架構:**
```
政府開放資料 API
     ↓ (你的後端定期抓取,例如每 10-30 分鐘一次)
你自己的小型後端/資料庫(存標準化後的資料)
     ↓ (App 只跟你自己的後端要資料)
手機 App
```

這個後端可以先做得很簡單——不需要複雜系統,一個小型 serverless function(定時觸發)+ 一個輕量資料庫,把整理好的 JSON 存起來,App 只需要呼叫你自己的一個簡單 API 即可。這部分之後交給 Claude Code 實作會很有效率,因為現在的資料格式與整理邏輯都已經明確。

## ✅ 後端架構決定(定案)

由於 MVP 階段確定**只服務西子灣單一地點**,不趕著擴充,採用最簡化方案,不需要資料庫:

```
GitHub Actions(定時任務,每15-30分鐘觸發一次)
     ↓
執行程式:
  1. 用氣象署授權碼,抓取三筆資料
     (F-A0021-001 潮汐 / O-B0075-001 海況 / A-B0062-001 日出日落)
  2. 套用本文件「標準化 + 缺值處理」邏輯
  3. 套用 color-logic.md 的紅黃綠燈判斷邏輯
  4. 輸出一份 xiziwan-status.json
     ↓
發布為公開網址(GitHub Pages,免費)
     ↓
App 只需定期抓取這個 JSON 網址並顯示
```

**選擇這個方案而非資料庫方案(如 Supabase)的原因:**
- 單一地點,資料量小,不需要資料庫的查詢彈性
- 完全免費,GitHub Actions 對這種低頻定時任務有充足免費額度
- 氣象署 API 授權碼存於 GitHub Secrets,不會被打包進 App 遭反編譯外流
- App 端邏輯單純:只需抓一個 JSON 網址,不用直接處理氣象署 API 或金鑰

**若未來擴充至多地點,才需考慮換成 Supabase 等資料庫方案**(可儲存多地點資料、支援更複雜查詢),目前不必超前部署。
